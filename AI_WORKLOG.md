- **Роль агента:** перевірка поведінки стендів, код, прогони, документація.

## 2. Де агент помилявся або міг помилитися

### 2.1. Хибне припущення про CSS-клас помилки (TC-09)
- **Що сталося:** перевірочний скрипт показав, що поле з помилкою має класи `input_error form_input error`. Агент вирішив, що помилку позначає `input_error`, і написав `not.toHaveClass(/input_error/)` для стану після закриття помилки.
- **Як помічено:** тест упав на першому ж прогоні. У звіті було видно `Received: "input_error form_input"`: клас `input_error` є в поля завжди, а помилку позначає окремий клас `error`.
- **Висновок:** стан елемента треба порівнювати в обох станах (є помилка / немає помилки), а не робити висновок з одного знімка.

### 2.2. SPA: URL змінюється раніше, ніж DOM (TC-12)
- **Що сталося:** після кліку на товар тест перевіряв `toHaveURL(...id=4)`, а відразу після цього брав назву товару через `inventory-item-name`. URL уже був новий, але на сторінці ще лишався каталог із 6 такими елементами.
- **Як помічено:** перший прогін упав зі `strict mode violation: resolved to 6 elements`.
- **Висновок:** після переходу чекати елемент, який є тільки на новій сторінці (`back-to-products`). Правило внесено в `CLAUDE.md`, щоб агент не повторив помилку.

### 2.3. Ненадійний перевірочний скрипт мало не дав хибних «фактів»
- **Що сталося:** скрипти, якими агент досліджував сайт, читали стан через `count()` і `textContent()` без очікування рендеру. Через це вийшло три сумнівні результати:
  - на сторінці 0 кнопок *Add to cart*: скрипт упав;
  - бейдж зник після повторного логіну, хоча кількома рядками нижче той самий бейдж показав 6;
  - після *Reset App State* у кошику лишилося 6 товарів.
- **Як помічено:** результати суперечили одне одному в межах одного прогону. Агент не переніс їх ні в тести, ні в баг-репорти, а позначив ці сценарії як нестабільні. Перед написанням баг-репортів ці сценарії перевірено повторно, вже з явним очікуванням рендеру. «6 товарів після reset» виявилося артефактом скрипта. Справжній дефект інший: кошик очищається, а кнопки лишаються «Remove» (BUG-03).
- **Висновок:** перевірочні скрипти потребують тих самих очікувань, що й тести. Суперечливе спостереження перевіряється повторно, а не записується як факт.

## 3. Ключові промпти

Промпти, з якими зібрано репозиторій, переписані в чітку форму: контекст, завдання, обмеження, критерії готовності. Їх можна повторно використовувати як шаблони.

Загальне правило: промпт описує **результат і спосіб його перевірки**, а не тільки дію. Слова «зроби тести» замало. Треба вказати, які сценарії, як перевірити, що тести стабільні, і що вважається готовим.

### 3.1. Базовий UI-набір для saucedemo

```text
Створи UI-автотести на Playwright Test + TypeScript для https://www.saucedemo.com під standard_user / secret_sauce.

Сценарії:
- позитивні (5): логін → каталог; каталог (6 товарів, назва, ціна $X.XX, кнопка); сортування; кошик (додати 2, бейдж, видалити 1); повний чекаут з перевіркою, що Item total = сума цін, Total = Item total + Tax, і є фінальне повідомлення;
- негативні та граничні (3): locked_out_user і невірний пароль; відкриття /inventory.html без логіну; чекаут з порожніми полями.

Обмеження:
- Page Object (pages/), кастомні фікстури (tests/fixtures.ts), фікстура loggedIn;
- селектори лише через data-test (testIdAttribute у конфігу) → getByTestId;
- лише web-first assertions; жодних waitForTimeout;
- тексти помилок перевіряти дослівно; перед написанням перевір їх на живому сайті.

Готово, коли: tsc без помилок; набір зелений при --repeat-each=10; README містить таблицю покриття (ID, сценарій, тип, файл) і команди запуску.
```

### 3.2. Розширення до 12 тестів з описом поведінки системи

```text
Розшир UI-набір до 12 тестів. Усі нові тести мають бути негативними або граничними. Нумерацію TC-NN продовжуй.

Кандидати (перед написанням перевір поведінку на живому сайті):
- валідація форми логіну: порожні поля, підсвітка полів, закриття помилки «×», порожній пароль, регістр логіна;
- межі кошика: усі 6 товарів, збереження після reload, видалення до нуля (бейдж зникає);
- захищені сторінки після logout (/cart.html, /checkout-step-one.html);
- сторінка товару з валідним і неіснуючим id.
Також розшир тест сортування на всі 4 опції.

Сценарії, поведінка яких на сайті нестабільна або неоднозначна, не автоматизуй, а перелічи окремо з причиною.

У README для кожного з 12 тестів додай розділ «Кроки / Поведінка системи»: що робить тест і як реагує сайт (URL, тексти, стан бейджа тощо). Дефекти, знайдені по ходу, познач як «Спостереження», а не як падіння тесту.

Готово, коли: tsc без помилок; 12 тестів × --repeat-each=5 зелені; README оновлено. Не коміть.
```

### 3.3. Спільна сесія і один воркер

```text
Переведи набір на workers: 1, щоб тести, яким потрібен залогінений користувач, не логінилися щоразу заново.

Вимоги:
- логін один раз за прогін через worker-scoped фікстуру; тести отримують ту саму сторінку;
- перед кожним тестом скидай стан, щоб тести не залежали від порядку: порожній кошик, сторінка каталогу; якщо сесія протухла, логінься повторно;
- тести логіну, доступу без логіну і logout лишаються в чистому контексті; поясни, чому кожен із них не може бути в спільній сесії;
- зміни в самих тестах мінімальні: в ідеалі лише імпорт іншої фабрики test.

Доведи, що логін відбувається рівно один раз (тимчасовий лог, потім прибери його). Перелічи компроміси: ізоляція, поведінка після падіння, --repeat-each.

Готово, коли: набір зелений, підхід описано в README.
```

### 3.5. API-тести restful-booker

```text
У тому ж репозиторії додай API-тести для https://restful-booker.herokuapp.com (документація: /apidoc) на Playwright request, без браузера, окремим проєктом `api` у playwright.config.ts.

Флоу (один тест, кожен етап у test.step): POST /auth → POST /booking (перевір тіло відповіді й GET) → PUT (перевір GET) → PATCH одного поля (інші поля не змінилися) → DELETE → GET повертає 404.

Негативні (3–4): невірні облікові дані; PUT/PATCH/DELETE без токена і з невалідним токеном (дані не змінилися); неіснуюче й уже видалене бронювання; невалідне тіло запиту.

Обмеження:
- клієнт api/BookingClient.ts повертає сирі APIResponse; статуси перевіряє тест;
- спершу прожени весь флоу через curl і зафіксуй фактичні коди; нестандартні коди (наприклад, 201 на DELETE) перевіряй як є, з коментарем «Особливість API»;
- кожен тест видаляє створені ним дані; унікальні тестові дані, бо стенд публічний.

Готово, коли: tsc без помилок; API --repeat-each=3 зелений; повний набір зелений; README має розділ API з описом кожного тесту й переліком особливостей API. Не коміть.
```

### 3.6. CI на GitHub Actions

```text
Налаштуй GitHub Actions: на кожен push у будь-яку гілку і вручну — npm ci → typecheck → встановлення Chromium → усі тести (UI + API).

- новий push у ту саму гілку скасовує попередній прогін (concurrency);
- HTML-звіт завантажується як артефакт завжди, крім скасованого прогону; test-results (трейси, скріншоти) — лише при падінні; зберігати 14 днів;
- у CI: retries 1, forbidOnly, репортер github для анотацій.

Перевір конфіг локально з CI=1 і без перевизначення --reporter.
```

### Що робить промпт чітким

| Поверхнево | Чітко |
|---|---|
| «зроби тести на логін» | які саме кейси, які тексти помилок перевірити, де лежать page objects |
| «додати негативні тести» | скільки, які кандидати, що робити з нестабільною поведінкою |
| «опиши результат» | формат: кроки + поведінка системи, дефекти окремо як спостереження |
| «без релогіну для однотипного сету тестів» | механізм (worker-scoped фікстура), скидання стану, які тести виключити й чому, як довести |

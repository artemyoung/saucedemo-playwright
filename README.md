# SauceDemo + Restful-booker — Playwright + TypeScript автотести

[![Playwright Tests](https://github.com/artemyoung/saucedemo-playwright/actions/workflows/playwright.yml/badge.svg)](https://github.com/artemyoung/saucedemo-playwright/actions/workflows/playwright.yml)

Автотести на **Playwright Test** + **TypeScript**:
- **UI**: демо-магазин [saucedemo.com](https://www.saucedemo.com/) (Swag Labs), патерн Page Object; 12 тестів.
- **API**: [restful-booker](https://restful-booker.herokuapp.com/apidoc), REST API бронювань; 5 тестів.

Хід роботи з AI-агентом, ключові промпти та розбір помилок описано в [AI_WORKLOG.md](AI_WORKLOG.md).

## Як запустити

Потрібен Node.js 20+.

```bash
npm ci
npx playwright install chromium

npm test               # усі тести: UI + API (headless)
npm run test:saucedemo # лише UI
npm run test:api       # лише API
npm run test:headed    # з відкритим браузером
npm run test:slow      # з відкритим браузером і затримкою 700 мс між діями
npm run test:ui        # інтерактивний UI-режим Playwright
npm run report         # HTML-звіт останнього прогону
npm run typecheck      # перевірка типів TypeScript
```

Окремий тест, файл або своя затримка:

```bash
npx playwright test -g "TC-05"
npx playwright test tests/login.spec.ts
SLOWMO=1000 npx playwright test -g "TC-05" --headed
```

**CI.** GitHub Actions ([playwright.yml](.github/workflows/playwright.yml)) на кожен push у будь-яку гілку, а також вручну, запускає typecheck і всі тести. HTML-звіт зберігається як артефакт `playwright-report`, а при падінні додається ще `test-results` з трейсами та скріншотами. Як переглянути звіт: *Actions → прогін → Artifacts*, завантажити архів, розпакувати й виконати `npx playwright show-report <папка>`.

| Що | Чому |

| Інші користувачі saucedemo: `problem_user`, `performance_glitch_user`, `error_user`, `visual_user` | Кожен із них спеціально містить дефекти. Щоб покрити їх, потрібна окрема матриця очікуваних результатів для кожного, а не та сама схема тестів. |
| Firefox, WebKit, мобільні розміри екрана | Навчальний обсяг і час CI. Додається одним рядком у `projects` |
| Візуальна регресія, доступність (a11y), продуктивність | Окремі види тестування з окремими інструментами (скріншот-порівняння, axe, Lighthouse) |
| Знайдені баги BUG-01…03 як автотести | Описані нижче як баг-репорти. Якщо додати їх як звичайні тести, CI стане червоним через дефекти стенду, а не через проблеми в тестах. Можна додати як `test.fail()`, щоб помітити, коли баг виправлять |
| Зовнішні посилання (*About* → saucelabs.com, соцмережі у футері) | Сторонні сайти поза межами тестованого продукту |
| Межі полів чекауту (довжина, спецсимволи, формат індексу) | Сайт перевіряє лише, що поля заповнені, а специфікації, з якою можна звірятися, немає |
| Сторінки всіх 6 товарів | Покрито одним представницьким товаром (`id=4`) і граничним `id=999` |
| API: `GET /booking` з фільтрами, формати XML і form-urlencoded, Basic auth замість токена, `/ping` | Поза межами заданого флоу. Basic auth і `/ping` перевірено вручну, вони працюють |
| API: бізнес-валідація дат (checkout раніше за checkin, дати в минулому) | Правил немає в документації, тож очікуваний результат невідомий |
| Навантаження на API | Публічний спільний стенд, навантажувати його некоректно |

## Знайдені баги

Перевірено 2026-11-24 на Chromium (Playwright), користувач `standard_user`. Кожен баг відтворено повторно перед описом.

### BUG-01: Можна оформити замовлення з порожнім кошиком
- **Серйозність:** висока (створюється порожнє замовлення)
- **Кроки:**
  1. Увійти як `standard_user` / `secret_sauce`, кошик порожній.
  2. Натиснути на іконку кошика, потім *Checkout*.
  3. Заповнити *First Name* = `A`, *Last Name* = `B`, *Zip* = `1`, натиснути *Continue*.
  4. Натиснути *Finish*.
- **Очікуваний результат:** кнопка *Checkout* у порожньому кошику неактивна або з'являється повідомлення «Cart is empty». Замовлення не створюється.
- **Фактичний результат:** відкривається крок 2 з *Item total: $0*, *Tax: $0.00*, *Total: $0.00*. Після *Finish* сайт показує **Thank you for your order!**. Додатково: *Item total* відображається як `$0` без копійок, на відміну від інших сум у форматі `$X.XX`.

### BUG-02: Неіснуючий товар додається в кошик, бейдж рахує «привида»
- **Серйозність:** середня
- **Кроки:**
  1. Увійти як `standard_user`, кошик порожній.
  2. Відкрити `https://www.saucedemo.com/inventory-item.html?id=999`.
  3. Натиснути *Add to cart*.
  4. Відкрити кошик.
- **Очікуваний результат:** для неіснуючого товару показується сторінка 404 або повідомлення без кнопки *Add to cart*. Кошик не змінюється.
- **Фактичний результат:** сторінка показує заглушку **ITEM NOT FOUND** з «ціною» `$√-1` і активною кнопкою *Add to cart*. Після кліку бейдж кошика показує **1**, а в `localStorage['cart-contents']` записується `[999]`. Сама сторінка кошика при цьому порожня: лічильник не відповідає вмісту.

### BUG-03: *Reset App State* не оновлює кнопки в каталозі
- **Серйозність:** низька
- **Кроки:**
  1. Увійти як `standard_user`.
  2. Додати в кошик *Sauce Labs Backpack* і *Sauce Labs Bike Light*.
  3. Відкрити бокове меню, натиснути *Reset App State*.
- **Очікуваний результат:** бейдж кошика зникає, а кнопки обох товарів повертаються в стан *Add to cart*.
- **Фактичний результат:** бейдж зникає, кошик справді порожній, але обидві кнопки в каталозі лишаються в стані **Remove**. Правильний стан з'являється лише після перезавантаження сторінки.

### BUG-API-01: Неповне тіло `POST /booking` повертає 500 замість 400
- **Серйозність:** середня
- **Кроки:** `POST https://restful-booker.herokuapp.com/booking`, заголовки `Content-Type: application/json` і `Accept: application/json`, тіло `{"lastname": "User"}`.
- **Очікуваний результат:** **400 Bad Request** з описом, яких полів бракує.
- **Фактичний результат:** **500 Internal Server Error**, тіло `Internal Server Error`. Помилка валідації виглядає як збій сервера.

### BUG-API-02: Невдала авторизація повертає 200
- **Серйозність:** низька
- **Кроки:** `POST /auth` з тілом `{"username": "admin", "password": "wrong"}`.
- **Очікуваний результат:** **401 Unauthorized**.
- **Фактичний результат:** **200 OK** з тілом `{"reason": "Bad credentials"}`. Клієнт не може відрізнити успіх від помилки за статусом, лише за тілом відповіді. Документація відповідь на помилку не описує.

### BUG-API-03: Дії з видаленим бронюванням повертають 405 замість 404
- **Серйозність:** низька
- **Кроки:** створити бронювання, видалити його (`DELETE /booking/{id}` з токеном), повторити `PUT` або `DELETE` для того ж `id` з токеном.
- **Очікуваний результат:** **404 Not Found**, як для `GET` того ж `id`.
- **Фактичний результат:** **405 Method Not Allowed**. Відповідь неконсистентна з `GET` і хибно вказує, що метод не підтримується.

> **Не баг, а особливість:** успішний `DELETE /booking/{id}` повертає **201 Created**. Для HTTP це нетипово (зазвичай 200 або 204), але саме так описано в [документації API](https://restful-booker.herokuapp.com/apidoc/index.html#api-Booking-DeleteBooking), тож відносно специфікації це коректна поведінка.

Тести TC-12 і TC-API-02/04/05 фіксують **фактичну** поведінку, тож CI лишається зеленим. Якщо баг виправлять, відповідний тест впаде, і це буде сигналом оновити очікування.

## Детальний опис тестів

### UI

#### TC-01: успішний логін
**Кроки:** відкрити `/`, ввести `standard_user` / `secret_sauce`, натиснути *Login*.
**Поведінка системи:** відкривається `/inventory.html` із заголовком **Products** та іконкою кошика в шапці.

#### TC-02: вміст каталогу
**Кроки:** після логіну перевірити кожну картку товару.
**Поведінка системи:** у каталозі рівно 6 товарів. У кожного є непорожня назва, ціна у форматі `$X.XX` і кнопка **Add to cart**.

#### TC-03: сортування
**Кроки:** по черзі вибрати в списку сортування Z→A, A→Z, ціну low→high і high→low.
**Поведінка системи:** список одразу перебудовується без перезавантаження сторінки. Назви йдуть в алфавітному або зворотному порядку, ціни за зростанням або спаданням.

#### TC-04: додавання та видалення з кошика
**Кроки:** додати *Sauce Labs Backpack* і *Sauce Labs Bike Light*, відкрити кошик, видалити рюкзак.
**Поведінка системи:** бейдж показує **2**. У кошику (`/cart.html`) обидва товари йдуть у порядку додавання. Після видалення лишається тільки Bike Light, а бейдж змінюється на **1**.

#### TC-05: повний чекаут
**Кроки:** додати 2 товари, перейти в Checkout, ввести ім'я, прізвище й індекс, натиснути *Continue*, потім *Finish*.
**Поведінка системи:** на `/checkout-step-two.html` *Item total* дорівнює сумі цін товарів, а *Total* дорівнює *Item total + Tax*. Після *Finish* відкривається `/checkout-complete.html` із текстом **Thank you for your order!**, а кошик очищається (бейдж зникає).

#### TC-06: заблокований користувач і невірний пароль
**Кроки:** увійти як `locked_out_user`, потім як `standard_user` з неправильним паролем.
**Поведінка системи:** вхід не відбувається, сторінка лишається на `/`. Тексти помилок:
- заблокований: *Epic sadface: Sorry, this user has been locked out.*
- невірний пароль: *Epic sadface: Username and password do not match any user in this service*

#### TC-07: каталог без логіну
**Кроки:** у новій сесії відкрити `/inventory.html` напряму.
**Поведінка системи:** доступ закрито. Показується форма логіну з помилкою *Epic sadface: You can only access '/inventory.html' when you are logged in.*

#### TC-08: валідація форми чекауту
**Кроки:** на першому кроці чекауту натиснути *Continue* з порожніми полями, потім заповнити ім'я та прізвище без індексу.
**Поведінка системи:** поля перевіряються по одному, зверху вниз. Спершу *Error: First Name is required*, потім *Error: Postal Code is required*. Перехід на наступний крок не відбувається.

#### TC-09: валідація форми логіну
**Кроки:** натиснути *Login* з порожніми полями, закрити помилку кнопкою «×», ввести логін без пароля, ввести логін іншим регістром (`Standard_User`).
**Поведінка системи:**
- порожня форма: *Epic sadface: Username is required*, обидва поля підсвічуються червоним;
- кнопка «×» прибирає і повідомлення, і підсвітку полів;
- без пароля: *Epic sadface: Password is required*;
- логін чутливий до регістру, тому `Standard_User` не підходить: *Username and password do not match any user in this service*.

#### TC-10: кошик на межах
**Кроки:** додати всі 6 товарів, перезавантажити сторінку, відкрити кошик і видалити товари по одному.
**Поведінка системи:**
- верхня межа: бейдж показує **6**, на сторінці не лишається жодної кнопки *Add to cart*;
- після reload кошик зберігається, бо його стан лежить у `localStorage`;
- нижня межа: коли видалено останній товар, кошик порожній, а бейдж зникає зовсім (а не показує «0»).

#### TC-11: доступ після logout
**Кроки:** увійти, вийти через бокове меню (*Logout*), потім напряму відкрити `/cart.html` і `/checkout-step-one.html`.
**Поведінка системи:** після виходу відкривається форма логіну. Обидві захищені сторінки недоступні: сайт показує форму логіну з помилкою, де названо саме ту сторінку, яку намагалися відкрити (*You can only access '/cart.html' when you are logged in.*).

#### TC-12: сторінка товару, валідний і неіснуючий id
**Кроки:** відкрити *Sauce Labs Backpack* з каталогу, потім напряму відкрити `/inventory-item.html?id=999`, натиснути *Back to products*.
**Поведінка системи:**
- валідний товар (`id=4`): правильна назва і ціна **$29.99**;
- неіснуючий `id=999`: сайт не падає і не перенаправляє, а показує сторінку-заглушку з назвою **ITEM NOT FOUND** і некоректною «ціною» (не у форматі `$X.XX`); дефект описано в BUG-02;
- з цієї сторінки можна повернутися в каталог, там знову 6 товарів.

### API

Тести працюють через вбудований у Playwright `request`, без браузера: окремий проєкт `api` зі своїм `baseURL`. Авторизація адміністратора (`admin` / `password123`, публічні дані з документації) дає токен, який передається в заголовку `Cookie: token=...`. Тести створюють власні бронювання з унікальним прізвищем і видаляють їх після себе, бо стенд публічний.

#### TC-API-01: повний цикл бронювання
Тест складається з кроків (`test.step`), і кожен крок видно окремо в HTML-звіті.
1. **POST /auth** з даними адміністратора повертає **200** і `{"token": "..."}`.
2. **POST /booking** повертає **200**, `bookingid` і збережене бронювання, яке повністю збігається з надісланим. Наступний **GET /booking/:id** повертає ті самі дані.
3. **PUT /booking/:id** з токеном повертає **200** і нову версію бронювання. Повторний GET підтверджує, що зміни збережено.
4. **PATCH /booking/:id** з `{"totalprice": 250}` повертає **200**. Змінюється лише ціна, інші поля лишаються як були.
5. **DELETE /booking/:id** з токеном повертає **201 Created**, як і задокументовано.
6. **GET /booking/:id** повертає **404 Not Found**: бронювання видалено.

#### TC-API-02: невірні облікові дані
**Кроки:** POST /auth з неправильним паролем, з невідомим користувачем і з порожніми полями.
**Поведінка системи:** у всіх трьох випадках відповідь **200** з тілом `{"reason": "Bad credentials"}` і без токена (див. BUG-API-02).

#### TC-API-03: зміни без авторизації
**Кроки:** створити бронювання, потім спробувати PUT, PATCH і DELETE двічі: без токена і з вигаданим токеном.
**Поведінка системи:** кожен запит отримує **403 Forbidden**. Подальший GET показує, що бронювання не змінилося і не видалене.

#### TC-API-04: неіснуюче та видалене бронювання
**Кроки:** GET неіснуючого id (`999999999`) і нечислового (`abc`), потім видалити створене бронювання й повторити з ним GET, PUT і DELETE.
**Поведінка системи:**

- PUT і DELETE уже видаленого бронювання повертають **405** (див. BUG-API-03).

## Підходи

- **Селектори через `data-test`**: у конфігу задано `testIdAttribute: 'data-test'`, тому використовується `page.getByTestId(...)`.
- **Page Object + фікстури**: тести не працюють із селекторами напряму.
- **Спільна сесія, 1 воркер**: тести, яким потрібен залогінений користувач (TC-02, 03, 04, 05, 08, 10, 12), використовують `sessionTest`. Логін відбувається **один раз за прогін** у фікстурі `sessionPage` рівня воркера. Перед кожним тестом сесія скидається: очищається кошик (`localStorage['cart-contents']`) і відкривається каталог. Якщо cookie сесії протухла, тест логіниться повторно. Тести логіну, доступу без логіну та logout (TC-01, 06, 07, 09, 11) працюють у чистому контексті через звичайний `test`. Якщо тест падає, Playwright перезапускає воркер, і наступні тести отримують нову сесію.
- **Web-first assertions** (`toHaveText`, `toHaveCount`, `toHaveURL`) з автоочікуванням. Перед `allTextContents()` (воно не чекає) стоїть явне очікування стану сторінки.
- **SPA-нюанс**: після кліку URL змінюється раніше, ніж оновлюється DOM, тому після `toHaveURL` тест чекає елемент, який є тільки на новій сторінці (наприклад, *Back to products*).
- **API-клієнт** повертає сирі `APIResponse`, тож статус-коди перевіряє тест. Нестандартні коди перевіряються як фактична поведінка і мають коментар `// Особливість API`.
- **Стабільність**: UI-набір прогнано з `--repeat-each=5` (60/60), API з `--repeat-each=3` (15/15).
